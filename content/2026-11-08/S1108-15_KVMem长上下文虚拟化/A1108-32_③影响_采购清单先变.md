【备选标题】
1. 10M 工作区的账：显存多 1 GiB，盘要 324.2 GiB
2. 长上下文不再问显存够不够，开始问盘够不够
3. 能记多久这件事，从显卡预算挪到了存储预算

【正文】
服务器上跑到 10M token 工作区，显存占 34.9 GiB，比 256K 档的 33.9 GiB 只多 1 GiB；同一张表里，NVMe 从 8.5 GiB 涨到 324.2 GiB。这条曲线一出来，容量规划的口径就换了：过去问显存能塞多少上下文，现在要问盘能留多少历史。

先看清它没做什么。论文第 7 章第一句就写明，KVMem 虚拟化的是可寻址的工作区，不延长单次推理里共同注意的 token 数。每一步仍然只在一个受窗口和显存约束的执行视图里跑。所以它不是把窗口变大，是让历史有地方待着。

三类人的账本要改

第一类是自己部署的团队。过去算容量是显存减权重、再看能剩多少给 KV，现在要多算一条主机内存和盘。服务器那张表里，主机内存列从 18.0 GiB 一路顶到 64.0 GiB 的上限，NVMe 从 8.5 GiB 到 324.2 GiB。

第二类是跑智能体的团队。DeepSWE 那组对照里，同一模型同一批任务，预填充时间从 211.5 秒降到 95.0 秒，降 55.1%；请求总时长从 48.1 分钟到 40.7 分钟，降 15.4%；端到端时间从 52.5 分钟到 45.8 分钟，降 12.8%；任务成功率从 43.8% 到 48.4%，论文原文写的绝对提升是 4.7 个百分点，31 次成功对 28 次。

这三笔时间账比成功率更值得看。预填充降了一半以上，端到端只降 12.8%，说明省下来的时间被别的环节吃掉了。智能体跑一轮要调很多次工具，模型算得快不等于任务完成得快。

第三类是做长文档处理的人。这里得说清楚：论文的五个设置全部落在长上下文 agent 基准上，没有长文档问答的对照。稀疏性这个前提在代码任务里成立，换成长文连续阅读是否还成立，没有证据。把结论直接搬到文档场景，是超出证据范围的。

四处得先泼冷水

一是它不能盖在闭源 API 上。第 7 章写得很明确：当前实现需要控制 KV 分配、检索、位置重建和分层搬运，无法在黑盒 API 之上透明地加一层。也就是说，这条路只对能自己掌控推理栈的人开放。

二是存储换的是真金白银。10M 工作区要 324.2 GiB 的 KV 存储，检索索引还要另算，从 256K 时的约 0.25 GiB 涨到 10M 时的 9.5 GiB。论文自己也把这条列为限制：KV 状态比文本大得多，工作区越大，主机内存、盘、索引和检索开销一起涨。

三是复用不等于重算。论文承认，复用历史 KV 与新上下文下重新计算并不数学等价，因为历史 KV 是在它当时的因果上下文里算出来的。另外，检索本身有失手率：一步之内只取回一部分块，该用的那块没被选中，模型就只能凭剩下的推断。

四是覆盖范围窄。NInfer 后端覆盖 Qwen3.5 稠密系列与 Qwen3.6/3.8 27B，另一个后端只覆盖 qwen35moe 架构的 GGUF，llama.cpp 那条路还会跳过滑动窗口注意力与纯循环架构的模型。README 另有一句提醒：架构支持不等于每个尺寸、量化、特性组合都测过。

还有两个落地细节容易被忽略。官方要求运行包与模型的完整路径不能含中文字符，包括用户名与上级目录；SSD 分层默认关闭，显式指定目录才开，而且文件只对当前服务进程有效，重启不恢复。把它当长期记忆库来用，会失望。

我的判断

这轮先变的是采购清单和部署方式，不是模型排名。没有哪个模型变强，只是历史从显存搬到了盘上。对预算的影响是结构性的：显卡那一档可以不动，存储要按历史规模重新算。

真要试，按这个顺序走。第一步，量出你手上最长任务的历史峰值 token 数，按论文那个比例估存储，10M 对应 324.2 GiB。第二步，确认模型在支持清单里。第三步，装包前把路径里的中文清掉。第四步，跑一天真实任务，只盯两个数：生成速度够不够用，检索有没有漏掉关键块。

任何一步过不去就先别换。工具的价值在于它解决的那类问题真的发生在你身上。
