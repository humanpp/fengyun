【正文】
0sec Labs 把安全框架 0 放上了 GitHub，许可证是 MIT 或 Apache-2.0。发布时（2026 年 11 月 8 日至 9 日）的 README 称它为研究预览。它不是一个新模型，而是把模型与安全工具串起来的一套框架。

先看能直接核对的部分。仓库 2026 年 8 月 19 日建仓，主语言 TypeScript，抓取时有 1,133 个 star、141 个 fork、2,114 次提交；最新版本 v0.28.9 在 2026 年 11 月 9 日发布，提供 macOS、Linux 与 Windows 的二进制包，并附校验和文件。

它是编排层，不是模型

按 README 的说法，0 负责组织漏洞调查、代码审查、渗透测试、逆向工程、验证与修复这几类工作，模型要用户自备。它内置 assessment、verification、fix、research 等工作流模板，结果进 findings 队列或看板，另有 skills 与 memory 记录。

入口有三个：本地浏览器控制台、命令行、以及给其他 agent 调用的 MCP 服务。命令行可以直接跑工作流模板，也能把同一套会话共享给 MCP 客户端。

安装方式也写得很直接：一行 curl 脚本，下载对应平台的二进制，与 checksums.txt 比对 SHA-256，不一致就拒绝安装；脚本还会把安装目录写进 shell 配置，并带一个固定版本的 FoxGuard 静态分析器。要做二进制逆向，另需本地装 Ghidra 与 Java。

公司起于苏黎世，对外称获 Y Combinator 支持；公开资料里的联合创始人是 Doruk Tan Ozturk 与 Fabian Zbinden，仓库 README 也挂了 YC 标识。开源的本地版之外，还有付费托管服务 0cloud，做 PR 安全测试与依赖扫描。

许可证是双许可，MIT 或 Apache-2.0，使用者可择一遵守。但 README 与安全策略里都未见服务等级条款，发布时的定位也是研究预览。

它自称找到了哪些漏洞

官网研究页给出的三组数字是：30 多个已合并进 Linux 内核的零日、500 多个处于保密披露中的 CVE、30 多个软件系统。公开清单里能看到 jsonata 的 CVE-2026-77413、Wireshark 的 CVE-2026-15164、node-forge 的 CVE-2026-33896、protobuf.js 的 CVE-2026-44289，以及一批内核问题。

这些条目状态并不一致：公开清单里明确标注 Merged upstream 的只有少数几条，多数写的是 In review、Queued upstream，还有的 CVSS 尚未定级。所以“30 多个已合并”只是页首统计，不能按条目逐个数出来。

第三方能核到什么程度

独立安全博客 PlayCISO 在 2026 年 11 月 9 日逐个查了清单里的部分编号：node-forge、jsonata、Wireshark 与两个内核 CVE 在 NVD 里都有记录，但 NVD 不标注发现者。也就是说，漏洞存在可以查，归属只能算厂商口径。

内核条目大多链到 lore.kernel.org 的补丁邮件，署名是 @0sec.ai 的地址——这算一条旁证，但补丁署名同样不等于第三方核验。

同一篇核对还指出，官网首页称有 30 多亿台设备运行着它加固过的软件，这句话在研究页找不到对应记录。这类数字没有公开出处，引用时只能标注为厂商口径。

还有一个细节值得记住：研究页写明，处于保密期的发现要等修复后才公开。所以公开清单不是全量，数字偏小或偏旧都正常。

厂商自己的研究笔记也留了反面证据：一篇写二进制分析实验“定位到可疑代码，但没有确认触发”；另一篇写流水线把一个已知驱动漏洞误报成新问题。

判断

可信度要分三层看：仓库的形态、许可、入口，可以自己打开核对；CVE 记录存在与否，可以去 NVD 查；30 多个内核零日是否由这套框架发现、500 多个 CVE 如何构成，目前只有厂商口径。

想用，先看清它是研究预览；想引用它的战绩，等上游合并记录与独立复现。
