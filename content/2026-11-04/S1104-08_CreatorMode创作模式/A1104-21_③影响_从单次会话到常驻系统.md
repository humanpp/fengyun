【正文】
2026 年 10 月 31 日到 11 月 2 日，三天里 DeepSeek-Harness 团队放了两样东西：开源的 dsh-superagent，和一句话造插件的 Creator Mode。

分开看都是功能更新。合起来看，是同一件事的两面。

我翻完官方仓库，这类系统要人做的事只剩三件：看一眼、做出来、查一下。这三件也交出去之后，剩下的活全落在人身上。

它开始值班了

dsh-superagent 的定位很具体：只面向一个 GitHub 仓库。

有人在 Issue 或评论里 @ 它的账号，它建一张工单，在自己的会话和自己的目录里干活，干完回到原来的对话交付，通常是开一个 PR。飞书群里 @ 它也行。

常驻方式不玄。部署文档写的是用 tmux 起一个进程，一行脚本启动和停止。停止时最多等 5 分钟，不强杀。

巡检是写给别人看的。状态命令有四个退出码：0 正常，1 需要重启，2 局部报错、重启也没用，3 卡在配置上。官方建议在另一个窗口建一个每小时的定时任务去查它，只在出问题时说话。

钱和人先被改掉

第一类是写代码的人。

以前 Agent 是坐在你电脑上等人的工具，问一句答一句。现在它有独立账号、独立提交身份、独立的合并权限，同事会在 PR 里和它对话。团队多了一个要管信誉的"机器人同事"，Review 的活有一部分换成了读它的提交。

第二类是接外包和小团队。代码审查原来要请人，现在可以放一个会读仓库、会提 PR 的进程在那儿跑。省掉的是一部分人力，增加的是配置和维护。

第三类是在 AI 工具上做二次开发的人。Creator Mode 把"扩展一个 Agent 应用"的门槛从"懂 Cordis 框架"压到"能说清想要什么"。这扇窗不会一直开着。

权限这一层，官方写得很直白

部署文档有一句原话：worker 和 router 两个预设都以 danger-full-access 运行，身份就是操作者的系统账号，能读操作者的主目录；账号包装脚本只负责选凭据，不提供隔离。

想隔离，得自己开一个专用系统账户。

安全须知的措辞更硬。项目没做过安全审计，不能当成安全或可生产使用的工具；它能执行模型生成的代码和命令，不可信插件可能损坏宿主、增删文件、泄露数据与凭据；沙箱、审批和权限控制能降低风险，但不保证隔离。

一边是"一句话造出插件"，一边是"造出来的代码要有人看"。中间那条缝，就是去读 638 行 JS 的人。

执行这一层，它给自己上了几道闸

没被点名的工作不接，团队写了规则才接，而且先以"只记录不执行"的模式跑。

每张工单一个会话、一个目录，互不串味。回合结束后，后台任务最多再跑 30 分钟。

自动合并默认对它关着。默认指令只允许一种情况：PR 是它自己开的，检查通过，增删合计少于 200 行。

如果这条 200 行真能守住，破坏半径大致是可估的。

反方的话也得说

这些设计解决的是"接活以后别乱来"，没解决"接来的活里有没有坑"。

代码是 Agent 写的，需求是你描述的，装插件的是下一个人。整条链上没人逐行读过。会话统计这类插件碰不到文件，风险有限；碰 Git 凭据、碰仓库推送权限的插件，是另一回事。

还有个时间问题。Harness 现在是开发者预览版，官方在 README 里用大写字母提醒：会出现破坏兼容性的变更。一个每周升级、插件也每周变的常驻进程，运维成本不会低。

我的判断

常驻成为默认形态的那天，"AI 辅助开发"会变成"AI 值守开发"。

留意三个指标：官方会不会给社区插件加签名或审核名单；Creator Mode 生成的东西有没有权限提示；两个预设的默认权限会不会从全权限降下来。

这三条有答案之前，我的建议是先把 superagent 装在一台一次性虚拟机里，用一个专用系统账户，只给一个仓库的写权限。它出问题的时候，损失停在那台机器上。
